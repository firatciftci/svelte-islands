# svelte-islands 1.1

Written 2026-11-19, after 1.0.1, from an audit of the code and five feasibility studies run against the installed Svelte 5.57.3 and SvelteKit 3.1.1 (and the 3.4.0 source): bundle attribution, static-snippet inference, Svelte core, SvelteKit internals, and benchmark harnesses. Every number marked "measured" came from those studies; scratch experiments live in the session scratchpad, not the repo. 1.1 is a minor release: no breaking changes, and every item works with or without the Vite plugin unless it says otherwise.

## The thesis

1.0 proved the model. 1.1 makes it cheaper, more honest, and easier to trust:

- cut what a SvelteKit page actually pays for the library by a quarter
- skip hydration for islands that provably can't change, without anyone writing `hydrate="never"`
- make the first interaction fast without depending on idle prefetch having finished
- give shell-page islands one shared, live page state
- show users and agents exactly what each island costs, from the build to the field
- replace a flattering benchmark with one that's built to be checked

## Where 1.0.1 stands, measured

- `scripts/size.ts` (svelte external, gzip level 9): `<Island>` 11,340 B, all exports 12,786 B against a 12,800 B limit, 1,688 B lazy
- what a SvelteKit 3.1.1 page with one `<Island>` really pays over the same page without it: 14,116 B gzipped. The standalone number counts devalue (1,126 + 539 B) and Vite's preload helper (903 B), which Kit already ships, and leaves out about 4,700 B of Svelte runtime that the island's template pulls in and Kit doesn't
- the `transport` hook adds 1,321 B gzipped to every page, islands or not (`part.ts` about 850 B, `unpack.ts` about 680 B)
- in an app with at least one island, the Vite plugin adds 498 B to pages without islands, because the boot's imports land in Kit's global `client.imports`
- per-module share of the standalone chunk: `runtime.ts` 40.8%, `island.svelte` 15.6%, `wake.ts` 10.8%, devalue `parse` 9.9%, preload helper 8.0%, `part.ts` 5.3%, `unpack.ts` 4.2%
- default hydration for a server-rendered island is `["interaction"]` (`island.svelte`, `strategiesOf`); `render="client"` defaults to `["visible"]`
- the benchmark waits for network idle plus 1.5 s before the first sort (`site/bench/run.ts`, `SETTLE`), so the published first-sort parity depends on prefetch having finished; the plain page renders all 3,000 berths though `HarborTable` already has a `limit` prop; it runs in Chromium only, seven runs, with min and max as its only spread

## What 1.1 ships

### 1. A quarter off the real cost

The target is the number a SvelteKit user pays, not the standalone chunk.

- replace `<svelte:element this={as}>` in `island.svelte` with explicit `{#if as === "tbody"}` and `div` branches. `svelte:element` compiles to `$.element` plus `$.attribute_effect`, which pulls in Svelte's `attributes.js`, `shared/attributes`, and `bindings/select`. Measured: −2,636 B on a Kit page, +83 B standalone (the markup is written twice). The two branches' attribute lists come from one object, so they can't drift
- move the server-only adoption branch and the `server.record` block out of `island.svelte` and into `server.ts`, behind the `Scope` interface (`part.ts`, `Scope`). Measured: −577 B on a Kit page
- replace the `SvelteSet` behind `arrived` (`runtime.ts`) with a `$state` version counter in a `.svelte.ts` module, which drops `svelte/reactivity`'s set from the island. Estimated −500 B
- replace `class={["island", className]}` with a string, which drops `clsx` and `set_class` (257 B, measured as part of the template's imports)
- don't split small seams into dynamic imports: moving the deferred and fresh paths behind a lazy facade measured +232 B on a Kit page, because per-chunk overhead outweighs bytes that small. Making `refreshAll` lazy measured +339 B
- don't replace devalue: Kit already ships it, and the library reuses Kit's instance (measured: one copy in the build)
- the 7 KiB target from the first 2.0 draft is retired. With every feature intact, the measured floor is about 10.3 KiB on a Kit page

Expected after this section: about 10.6 KiB on a Kit page (measured prototype: 10,895 B), 10.6 KiB standalone (10,852 B), 12.0 KiB for all exports.

### 3. `hydrate="never"`, inferred

When an `<Island>` has no `hydrate` prop, `render` is absent or `"server"`, and the plugin can prove its snippet never changes, the plugin adds `hydrate="never"`. The island then downloads no code and no data on the first load, and skips the interaction interceptor and prefetch (`wake.ts`: never-only islands already do).

The rules, checked in `extract.ts` after `analyze()` succeeds in `visitIsland`, against the Svelte 5 AST:

- allowed: `Text`, `Comment`, `ExpressionTag`, `RegularElement`, `IfBlock`, `EachBlock`, `KeyBlock`, `SnippetBlock`, `RenderTag` of a static snippet, `HtmlTag`, `ConstTag`, `Attribute`, `SpreadAttribute`, `ClassDirective`, and `StyleDirective`, as long as every expression they hold reads only allowed captures
- rejected: `OnDirective`, `BindDirective`, `UseDirective`, `AttachTag`, `TransitionDirective`, `AnimateDirective`, `LetDirective`, `AwaitBlock`, `DebugTag`, `SvelteComponent`, `SvelteSelf`, `SlotElement`, `SvelteBoundary`, `SvelteHead`, `TitleElement`, `SvelteWindow`, `SvelteDocument`, `SvelteBody`, `SvelteFragment`, and `SvelteElement` with a non-literal `this`
- `Component` tags are rejected in 1.1; 2.0's component analysis (2.0, section 5) lifts this
- allowed captures: the snippet's own parameter (the part's value, which re-renders the island when its hash changes) and module imports. Rejected: every other capture, including `let`, runes, props, `each` items from outside the snippet, and page `data`, because they can change without the part's hash changing, which would leave stale HTML in place (`island.svelte` re-renders only on a new hash)
- rejected globals: `Date`, `Math`, `crypto`, `performance`, `window`, `document`, `navigator`, `localStorage`, `sessionStorage`, and `location`
- the scope walker records `kind: "local"` without mutability today (`extract.ts`, `declare*`); it gains a `mutable` flag set from the declaration form, so the capture rule is exact

Plain forms, links, `<details>`, and `<dialog>` with `commandfor` buttons stay static, because none of them need Svelte to work.

The same `hydrate="never"` goes into both the server and the client output, since shell pages record `hydrate` on the server. In dev, the island carries `data-island-why`, naming the first rule that kept it hydrating (or `inferred`), and `inspect`, the overlay, and the plugin's dev log show it.

One limit stays and is documented: after a client-side navigation, the island renders in the browser from its snippet, so it downloads its code then, whatever its strategy (`island.svelte`, the `{:else}` branch's effect).

### 4. A faster first interaction

The 1.0 benchmark showed first-sort parity only after prefetch finished. 1.1 makes the cold case good:

- intent boost: `pointerover`, `focusin`, and `touchstart` inside a waiting island start its part, code, and needs at high priority if prefetch hasn't fetched them. One delegated listener per root, attached with the interaction interceptor, so it costs no per-island listeners
- interaction islands move ahead of everything else in the hydration queue as soon as intent fires, not only when a click is held (`runtime.ts`, the queue's priority)
- `observe` gains a `prefetch` summary on `pagehide`: for each prefetched part, whether an island used it (`used`), never woke (`wasted`), or woke before it arrived (`late`)
- the benchmark's cold mode (section 9) is the gate: on slow 4G, the cold first sort on the islands page must be no worse than 1.5x the plain page's

### 5. One live page state on shell pages

On a SvelteKit page, every island reads the same page state. On a shell page, each island gets its own copy (`shell.svelte.ts`). In 1.1, the boot builds one scope per page from the snapshot, with each captured name as a single `$state` proxy, and gives every island getters and setters on that one object. A checkbox in one island then updates a count in another, as it does on a SvelteKit page.

- the server writes each captured name once per page instead of once per island, which also shrinks the boot JSON when islands share values
- functions still don't cross; 2.0 (section 3) fixes that by running the page script
- the "each island gets its own copy" paragraph in `docs/20-core-concepts/80-shell-pages.md` becomes "islands share the page's values"

### 6. Shell detection that doesn't depend on a regex

Shell pages are detected by matching Kit's inline start script (`NATIVE`, `server.ts` and `inspect.ts`). Kit 3 exposes no csr flag, at runtime or in `$app/manifest` (whose routes carry only `id`, `page`, and `endpoint`). The plugin knows the routes, though:

- the plugin builds a route-to-csr map at build time by reading `csr` exports from each `+page` and `+layout` (universal wins over server, the last node wins, matching Kit's `page_nodes.js`) and writes it into a virtual module the server imports
- `handle` checks `event.route.id` against the map; `NATIVE` stays as the fallback for pages without the plugin and for `csr` values the plugin can't read statically
- in dev, a disagreement between the map and the regex logs a warning naming the route, so a Kit change surfaces immediately

### 7. Tracing

Kit 3 made tracing stable. When `kit.tracing.server` is on, the library emits OpenTelemetry spans under Kit's current span, through the public `event.tracing.current` and a dynamic `import("@opentelemetry/api")`, so apps without tracing load nothing:

- `svelte-islands.page` around `inject`, with the island count and inline and external part bytes as attributes
- `svelte-islands.part.serialize` per part, with its name and bytes
- `svelte-islands.rebuild` and `svelte-islands.fresh`, with the page, the outcome (`ran`, `cooling`, `busy`, `barren`), and the queue length

In the browser, `observe` gains a `frame` event from the Long Animation Frames API (Chromium), attributing each long frame to the island whose hydration or replay ran in it.

### 8. Agents and tooling

- `svelte-islands mcp` starts an MCP server over stdio, with the JSON-RPC written in the package (no new dependency). Tools: `inspect_page` (the `inspect` output), `check_budget` (the budget check), `advise_page_data` (the overlay's page-data advisor, as JSON), and `explain_island` (why an island hydrates, from `data-island-why`)
- `llms.txt` and `llms-full.txt` built from `docs/` by the site build, linked from the README
- error codes: every thrown error and logged warning gets a stable code (`islands_private_in_public` and so on, the way Svelte names its errors) and a link to a troubleshooting section for that code. The `throw new Error("private")` sentinel in `island.svelte` becomes a typed error, and the `"await_invalid"` substring check in `server.ts` reads Svelte's error `code` when present, with the substring as the fallback
- `init` gains `paths.base` (it writes `prefix` when `kit.paths.base` is set), a store choice (`--store redis|r2|none`), and fixture tests over a dozen hooks-file shapes, including existing `sequence` calls, `export { handle }` forms, and a missing file. Text edits stay; 2.0's zero-config setup replaces them

### 9. A benchmark built to be checked

`site/bench/run.ts` is rewritten to these rules, and the benchmark page publishes whatever they produce, including the cases where islands lose:

- two modes, reported side by side: `cold` (wait for `load`, no settle, first sort as soon as the header button exists) and `settled` (today's behavior)
- interactions measured with the Event Timing API (`durationThreshold: 16`), plus the existing time to the visible `aria-sort` change as a second number
- bytes from CDP `Network.loadingFinished` (`encodedDataLength`) instead of the resource-timing buffer
- "blocking time" renamed to what it measures (long tasks from navigation to the end of the window), and a real TBT next to it
- three network profiles, each recorded in the output: Lighthouse's slow 4G (today's), slow 3G, and unthrottled; plus a mobile viewport (`isMobile`, `hasTouch`)
- Chromium, Firefox, and WebKit; the last two run unthrottled and are labeled that way, since CDP throttling is Chromium only
- at least 15 runs per cell, the true median, the IQR, and a seeded bootstrap 95% interval for each median and for the difference
- one JSON file per run under `docs/benchmark-raw/`, with a gzipped trace per run published as a release asset with checksums; full browser, OS, CPU, and git SHAs in the output
- three baselines: plain as it is today (labeled untuned), plain tuned (the existing `limit` prop with a "show all" control), and plain lazy (berths fetched from a `+server.ts` route near the viewport with the same 320 px margin), which is the fair comparison for a deferred island

Public harnesses, entries built in 1.1, posted by the owner:

- khromov/interactive-blogs-benchmark: `frameworks/sveltekit-islands` and `frameworks/sveltekit-islands-shell`, copied from `sveltekit-latest`, two entries in `frameworks.config.json` (about two days)
- ogygiajs/bench: `svelte-islands` and `svelte-islands-shell` apps for the blog and all five scenarios, registered in `suites/apps/frameworks.config.json`, passing each scenario's fidelity check, with the mapping of each scenario to library features written in each app's config header as the bench's rules require (about a week). Shop's personal bits map to `render="fresh"`, dashboard to islands with `query.live` left out, and ai-chat to `stream()` and `Await`

### 10. Tests where 1.0 had none

The audit found no direct unit tests for `wake.ts`, `island.svelte`, `shell.svelte.ts`, `vite.ts`, `Await`, `Pending`, `unroll`, `context`, or `devtools`. 1.1 adds them for everything this release touches: `wake.ts` (each mode's lifecycle against a fake runtime), `shell.svelte.ts` (shared scope), `vite.ts` (the splice and the post-build patch, against a scratch Vite build), and the static-snippet rules (accept and reject, one case per rule). The differential fuzz gains static-only snippets, and checks that after a scripted change of page data, an inferred island's HTML still matches a hydrated render, which is the check that catches stale HTML.

## Cut from 1.1, and why

- moving deferred, fresh, and replay code behind dynamic imports: measured larger, not smaller, at these sizes (+232 B)
- a 7 KiB runtime: not reachable with features intact (measured floor about 10.3 KiB on a Kit page)
- splitting prefetch into code on view and data on intent: it would undo the first-sort result 1.0 depends on; intent boost (section 4) gets the latency benefit without the regression
- Speculation Rules by default on shell pages: they already exist behind `handle({ speculation })`, and turning them on changes traffic for every shell page; they stay opt-in, and the docs recommend them
- AST-based `init`: superseded by 2.0's zero-config setup
- a real HTML parser for the skeleton tokenizer: a wrong skeleton is cosmetic, and 2.0 consolidates the skeleton code anyway
- compression dictionaries, streamed HTML insertion, and `prerender_until_script`: Chromium only or origin trials (watch list in `plans/2.0.md`)
- a workaround for kit#17763 (`csr = false` pages link CSS for components the render never used): pruning stylesheets in `transformPageChunk` is unsafe with islands, which render more components on wake; the fix belongs in Kit (owner action below)

## Owner actions for 1.1

- post the two benchmark entries (the code is ready in their own branches; nothing is opened for you)
- the RFC draft needs two corrections before sending: with a `pending` snippet, the server renders only the pending branch and no children, so a deferred boundary with `pending` has no server HTML to keep; and an `{#if}` mismatch re-renders only that branch, not the whole tree
- a PR to SvelteKit for kit#17763, drafted from the study: record each CSS file's scoped `svelte-<hash>` selectors at build time and, on `csr = false` pages, link a stylesheet only if it's unscoped or one of its hashes appears in the rendered body (about 150 lines plus tests in Kit's `build_server.js` and `render.js`). It fixes file-level leaks but not rules that share a file, and the PR should say so
