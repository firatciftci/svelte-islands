# svelte-islands 1.0

Written 2026-11-17 from an audit of 0.8.0 and two research passes. Revised the same day into the working plan for 1.0: what ships, what was cut and why, and a checklist that is ticked off as the work lands.

## The thesis

Write an ordinary SvelteKit app, and ship only the JavaScript and data a visitor actually uses.

Astro gives you zero JavaScript by default but you leave SvelteKit. ogygia gives small pages but a route turns SvelteKit's client off. Mochi is Bun only, with no client router. Qwik and Marko need a different component model. svelte-islands keeps SvelteKit's whole app model (routing, `load`, form actions, client navigation, context, and snippets that close over page state) and, in 1.0, defers code, HTML, data, and hydration.

## Where 0.8 stood

- an island renders its snippet in a separate server render and embeds the HTML; the browser hydrates the page, then each island later with `hydrate()` and the context captured by `getAllContexts()`
- island code was not split: the snippet and its imports shipped in the route chunk, so even a `when="never"` island cost its code
- everything outside islands hydrated in full
- the runtime was about 8.5 KB gzipped, and a docs page preloaded about 67 KB of JS
- the benchmark's weak spot was the first interaction: 717 ms for the first sort of the berths table against 237 ms on plain SvelteKit
- baseline: 216 unit tests and 42 end-to-end tests passing

## What 1.0 ships

### 1. Code waits too

An optional Vite plugin, `islands()` from `svelte-islands/vite`, moves each island's snippet into its own chunk for the browser build.

- parse each component with `svelte/compiler`, find `<Island>` children snippets, and work out what each one captures from the component's scope
- in the client build, rewrite the snippet into an exported snippet in a virtual module; every captured value reaches it through a `scope` object of live getters (and setters for anything the snippet assigns or binds), and the imports it uses are re-imported there
- remove imports the page no longer uses, so they leave the route chunk
- the island receives `code={() => import(...)}` and `scope={...}` and loads its code together with its part
- the server build is untouched, and the snippet in the virtual module renders the same markup, so hydration matches
- without the plugin everything works as before

### 2. Pages that don't hydrate

A route with `export const csr = false` keeps its islands working when the plugin is on. Only islands boot.

- a bootloader chunk finds island roots in the DOM and runs each island's lifecycle without a parent component
- shell islands get their value from the part, their captured page values as a serialized snapshot, and every context whose key can be named; functions don't cross, and the docs say so
- navigation is a real document navigation; `handle({ speculation })` adds Speculation Rules (prefetch or prerender on hover) and `handle({ viewTransitions: true })` adds cross-document View Transitions, so no custom router is needed

### 3. A faster first interaction

- once an island is near the viewport and the browser is idle, its part and code are fetched at low priority, skipped on `Save-Data` and slow connections, within a byte budget per page
- `observe` reports each prefetch and whether it was used, so waste is measured
- held input is replayed after hydration: clicks (as before), text typed into fields, and form submissions
- hydration already yields between slices with `scheduler.yield()`

### 4. Fresh islands

`render="fresh"` marks an island whose content depends on the request.

- the cached page carries a learned skeleton in its place
- `fresh(name, read, fallback)` from `svelte-islands/server` makes the island's part: the page render gets `fallback` and never calls `read`, so no visitor's data reaches the cached HTML or page data
- after load, the browser makes one request for every fresh island on the page; the server renders the page for that request with its cookies and returns only those islands' HTML and values, with `cache-control: private, no-store`, and every part made during that render is private
- after a client navigation, the island asks for its value the same way
- static parts stay content-addressed, so a deploy doesn't cold the CDN
- a prerendered page can't be rendered again (SvelteKit's server `fetch` hands prerendered paths to the network, where the adapter serves the file), so its fresh islands show the fallback; cache a server-rendered page with `cache-control` instead

### 5. Fewer bytes

- the skeleton learner and the packed-format decoder load on first use instead of with every page
- the boot path carries only what every island needs

### 6. Developer experience

- `npx svelte-islands init` sets up the transport, the handle, the stylesheet, and the Vite plugin
- `npx svelte-islands inspect <url>` reports every island on a page, with `--json` for agents and CI
- the overlay's advisor lists the page's data by size and shows which values should become parts
- combined triggers: `hydrate={["interaction", "idle"]}`, where the first one wins

### 7. Answering ogygia 0.14

ogygia 0.14 says context reaches every region and that each PR runs more than 10 million region test cases in three browsers. 1.0 meets both claims with its own tests and measurements.

- context already reaches every island on a hydrated page, through `getAllContexts()`. On a `csr = false` page, an island gets the contexts whose keys can be named: strings, `Symbol.for()` keys, and keys made with `context(name)` from svelte-islands. Their values are serialized with the same transport as parts, so dates, maps, and nested parts survive. A context the island can't get, because its key is an unnamed symbol or its value is a function, gets a warning in development that names the key, since a library may set contexts an island never reads. A page value the island reads that holds a function is an error.
- the end-to-end suite runs in Chromium, Firefox, and WebKit
- property tests with fast-check cover the packed format, the serializer, the skeleton learner, and the Vite plugin's capture analysis. The plugin test is differential: it generates components and checks that each renders the same HTML with and without the plugin. A CI mode raises the number of runs.

### Bytes, as measured

The packed-format decoder can't load lazily, because SvelteKit decodes page data synchronously while it hydrates. The encoder is the larger half, though, and it now stays on the server. With the learner loading on first use, `<Island>` costs 10.4 KiB gzipped up front against 10.6 KiB in 0.8, even with the new lifecycle, prefetching, and replay.

### API 1.0

```svelte
<Island part={data.orders} render="deferred" hydrate={["interaction", "idle"]}>
  {#snippet children(orders)}
    <OrderTable {orders} />
  {/snippet}
</Island>
```

- `render`: `"server"` (default), `"deferred"`, `"client"`, or `"fresh"`; replaces `defer` and `ssr`
- `reveal`: when deferred or fresh HTML is fetched (default `"visible"`); replaces `defer`'s strategy form
- `hydrate`: replaces `when`, and takes one strategy or several
- `learn`, `whenWanted`, `loadNow`, and `replay` stay public, because the docs have real uses for each (your own skeletons, lazy content that print and find in page need, and early clicks)
- `Pending` stays: it drives a skeleton from your own loading state, which `Await` can't

### Measurement

- island cost in `observe` and the overlay: code bytes, data bytes, HTML bytes, hydration time, and the time from first interaction to live
- the benchmark gains the plugin automatically, and the comparison is rerun for the release

## Cut from 1.0, and why

- the `sv` community add-on: the API is experimental and needs an npm scope; `svelte-islands init` does the same job from the package itself
- remote-function islands: remote functions are still experimental in SvelteKit 3, behind two flags; revisit when they're stable
- delta parts and shape dictionaries: Compression Dictionary Transport is Chromium only, can't run on static hosts, and only pays off for parts that change often; revisit with a real workload
- an HTML budget in CI: `svelte-islands check` already budgets pages
- remount-instead-of-hydrate: too app-specific to choose automatically
- a migration codemod: there are no users to migrate, and the advisor covers new apps
- an svdevtools panel: svdevtools is in early preview with no extension API
- reusing `hydratable` for inline parts: the existing transport works, and switching gains nothing measurable
- a public benchmark against ogygia and Astro: a separate repo to maintain; the in-repo benchmark compares plain SvelteKit and islands

## After 1.0: owner actions

These need you, not code: publishing the release, a Svelte RFC for lazy hydration boundaries, posting benchmark data on SvelteKit #1390, talking to the ogygia and Mochi maintainers, an electionsarchive.com case study, and finding co-maintainers.

## What 1.0 won't do

- resumability: the core team rejected it and it needs a different component model
- a custom client router: Speculation Rules and View Transitions cover shell routes, and SvelteKit's router covers the rest
- leaving SvelteKit
