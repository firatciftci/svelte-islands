# svelte-islands 2.0

Written 2026-11-19 and rewritten the same day from five feasibility studies run against Svelte 5.57.3 and SvelteKit 3.1.1 (and the 3.4.0 source). The first draft bet on "static regions": the plugin finding every static subtree in every template and skipping its hydration. The studies measured that idea and it didn't hold up for plain markup: hydrating 200 literal paragraphs took 0.80 ms with or without it, because Svelte's compiled template already returns static nodes without walking them. Its real gains are bytes, and component-heavy or `{#each}` content (2,000 rows: 4.0 ms hydrated against 0.8 ms adopted), and it's blocked in the general case by scoped CSS and by parents like `<table>` and `<ul>` that can't take a wrapper. This plan keeps the parts that measured well and drops the rest.

2.0 builds on 1.1 (`plans/1.1.md`) and is a major release: breaking changes are allowed, and each one has a codemod.

## The thesis

2.0 makes svelte-islands disappear into SvelteKit:

- setup is `islands()` in `vite.config`, and nothing else
- an island can `await`, and its content streams into the same response; no second request, no waiting for the whole page
- a `csr = false` page keeps full Svelte semantics: the page's script runs once, so islands share live state and functions
- a per-visitor island costs one island render, not a whole page render
- components that can never change never ship, wherever they're used
- one code path: the plugin is required, so there's no second server path to keep correct

Each of these was checked against the real source of Svelte and Kit. Two ideas that need Kit to change (trimming page data, and starting Kit's client later) are upstream asks with numbers attached, not 2.0 features.

## Targets

1.1's reworked benchmark and the ogygiajs/bench entries give the baselines. 2.0 ships when, against those 1.1 numbers:

- setup for a new app is one line, verified by a fixture app with no `hooks.server.ts` and no `hooks.ts`
- Kit marginal for one island stays at 10.8 KiB or less, with streaming and static components included
- on ogygiajs/bench's docs and blog scenarios in shell mode, JavaScript is lower than 1.1's shell mode, and the page script's own bytes are reported separately
- on the library's own page, a streamed island's content appears before the page's slowest `load` would have let the whole page render, measured with a 500 ms delayed island
- a fresh island's server cost is one island render: the fresh endpoint runs one reader and one render per request, measured by counting `load` calls in a test
- static components cut hydration time on a 200-instance fixture by at least 40% (measured in the study: 1.6 ms to 0.8 ms) and remove the components' code from the initial load
- every 1.x app migrates with `svelte-islands migrate` and passes its tests

## What 2.0 ships

### 1. One line of setup

Kit has no API for a library to register a handle or a transport, but it generates the modules that wire hooks in, and the plugin can transform those:

- server: Kit writes `.svelte-kit/generated/{dev,build}/server.js`, whose `get_hooks()` imports `hooks.server` if it exists and returns `{ handle, ... }` (Kit `core/sync/write_server.js`). The plugin rewrites that return to `handle: sequence(islandsHandle, handle ?? identity)` and adds the imports. With no hooks file, `handle` is `undefined`, and the library's handle is used alone
- client: Kit writes `generated/build/client/app.js` with `transport: universal_hooks.transport || {}` (`write_client_manifest.js`). The plugin merges the library's transport into that expression, and does the same for the server's transport
- every rewrite asserts exactly one match and throws a build error naming the Kit version otherwise, so a Kit change fails the build instead of silently dropping the library
- the stylesheet is injected by the plugin as a virtual CSS module in the root layout's chunk
- `islands({ hooks: false })` turns this off for people who want to call `sequence` themselves; then `handle` and `transport` are imported from `svelte-islands/server` and `svelte-islands/transport`
- a marker in the generated module prevents double installation when someone also adds the handle by hand, and dev warns when that happens
- `sequence` runs the outer handle's `transformPageChunk` last (`exports/hooks/sequence.js`), so the library's injection keeps running after the app's, as it does with `init` today
- Kit regenerates `generated/dev/server.js` when `hooks.server` changes, so the transform reruns; a test edits the hooks file in dev and checks the handle is still wrapped

Published alongside as an `sv` add-on, `npx sv add @svelte-islands/sv`, which adds the dependency and the plugin line. Unscoped `sv` add-on names are reserved, so this needs an npm organization (owner action).

### 2. Streamed islands

`render="streamed"` lets an island's snippet use `await`, and sends its finished HTML in the same response:

- on the server, `draw()` returns the island's skeleton in place at once, starts `render(Frame, { props, context, idPrefix })` detached, and records the promise on the request. `render()` returns a thenable, and awaiting it resolves when every `await` inside has (Svelte `server/renderer.js`)
- in `handle`, after `resolve()`, the library returns `new Response(response.body.pipeThrough(append), response)` without `content-length` and Kit's `etag`, since the body no longer matches them. `append` writes `<template data-island-for="id">…</template>` and a small swap script (with Kit's CSP nonce) as each render finishes, in completion order, after the page. HTML parsers put content that follows `</html>` into `body` (the "after after body" insertion mode), so the appended templates parse in place; an e2e test in all three engines confirms it before anything else in this section is built
- in the browser, the swap script moves the template's content into place and the island hydrates by its `hydrate` strategy, as a deferred island does. A failed render streams a fallback template, so the island shows `failed` instead of a stuck skeleton
- Kit doesn't stream page HTML (it awaits the render and sends one `text()`), and `transformPageChunk` runs once with `done: true`, so wrapping the body in `handle` is the only seam; it's public API
- Svelte's async mode is process-wide (compiling with `experimental.async` imports `svelte/internal/flags/async`), so `render="streamed"` requires `experimental.async`, and the island throws a coded error without it
- the island's reads of other parts are tracked synchronously today (`runtime.ts`, `reading()`), and reads after an `await` would be lost, which breaks the private-part and needs checks. Streamed renders run their reads inside `AsyncLocalStorage` instead; on Cloudflare Workers that needs `nodejs_compat`, which the docs say
- a streamed island can't be fresh or read a private part, since its HTML lands in a page that may be cached; both are coded errors
- request state must outlive `resolve()`: the stream holds it until the last island settles or a timeout (`streamTimeout`, default 10 s), and aborts on client disconnect
- `Await` and `stream()` keep working; the docs point slow-but-small content at `render="streamed"`, and long content at `render="deferred"`
- kill criterion: if any of Kit's adapters (node, cloudflare, vercel, netlify) buffers a streamed `Response` from `handle`, the feature ships only for the adapters that stream, with a table in the docs

### 3. Shell pages that run their script

On a `csr = false` page, the page's `<script>` never runs in the browser, so islands get a snapshot of the values they capture, and functions can't cross. In 2.0, the plugin compiles the page's instance script into a component with an empty template and an `expose` callback, and the boot mounts it once, detached, with the page's `data`, `form`, and `params`. Every island then closes over that one live scope. Measured in the study: islands mounted with the shell's contexts read them, a function in the shell updated both islands, and a write from an island reached the other.

The plugin runs the script only when all of these hold, and falls back to 1.1's shared snapshot otherwise, with a dev message naming the reason:

- no `bind:this` and no other template refs (the template doesn't exist in the browser)
- imports only from an allowlist (`svelte`, `svelte/*`, `svelte-islands`, `$app/environment`, `$lib` modules the plugin can see) or from modules the app opts in with `islands({ shell: { allow } })`
- no `$app/navigation`: its functions depend on Kit's client, which doesn't run on these pages
- `$app/state` is rewritten to a bridge module that serves `page.data`, `page.params`, `page.url`, `page.form`, and `page.status` from the boot JSON. Without the rewrite, `$app/state` silently returns its defaults on these pages (Kit's `state/client.svelte.js` is filled only by the client)
- no top-level `await` unless `experimental.async` is on

Page scripts with side effects (timers, fetches, listeners) now run in the browser, which is the point and also a change. So this is on by default only for pages whose scripts pass the rules, and `export const islandsScript = false` in a page turns it off. An ESLint rule in `svelte-islands/eslint` flags `$app/navigation` imports in `csr = false` pages.

Measured overhead beyond the Svelte runtime the islands already need: about 0.5 KiB gzipped for the glue, plus the page script's own compiled code, which shell pages don't ship today. `inspect` and the size report show the page-script bytes per route.

### 4. Fresh islands at the cost of one island

The fresh endpoint renders the whole page again for each visitor, so every `load` on the page runs per visit. In 2.0, a fresh island can name a reader that runs on its own:

```ts
/// file: src/islands/cart.server.ts
import { reader } from "svelte-islands/server";

export const cart = reader(async (event) => getCart(event.cookies));
```

```svelte
<Island part={data.cart} render="fresh" reader="cart">
```

- the plugin collects `src/islands/*.server.ts` into a registry the server imports
- when the page renders, each fresh island with a reader writes its signed scope: the page values it captures, serialized with the part transport and signed with HMAC-SHA-256 under `SVELTE_ISLANDS_KEY` (generated by `init` and read from the environment, so it survives deploys and is the same on every instance). The values come from the cached public render, so they're signed for integrity, not encrypted. A part the island reads is sent by hash, not by value
- `/_parts/fresh` verifies each scope, runs each reader once with the visitor's request, renders each island's module alone with `render(Frame, …)`, and returns them in one private response, as today
- the browser sends the scopes it got from the page, so nothing per visitor ever goes into the page's HTML
- an island without a reader keeps 1.x's whole-page render
- requests stay GETs; the scopes travel in the query when they fit in 2 KiB and in a `POST` body otherwise, which is fine because fresh responses are private and never cached
- with remote functions stable, a reader can be a remote `query` instead; until then, readers are plain server modules
- kill criterion: if the signed scope for the median fixture island is over 1 KiB, the reader path is limited to islands whose captures are parts only

### 5. Static components

The narrowed form of static regions, which the studies found sound: the unit is a component, not an arbitrary subtree.

- a component is static if its template passes 1.1's static-snippet rules, every component it renders is static, and its script declares only `$props()`, constants, imports of static modules, and pure functions, with no `$state`, `$derived`, `$effect`, lifecycle functions, `getContext`, stores (`$store`), `$app/state`, or top-level calls
- the plugin decides this once per module, cached by content hash; components from `node_modules` aren't analyzed and count as dynamic. Measured cost: 0.35 ms to parse a file and 1.3 ms to analyze a 200-paragraph island, far under any build budget
- when a page or layout renders a static component, the plugin compiles that instance as an adoption point: on the server it renders normally; when the page hydrates, the parent adopts the component's nodes through `{@html}` without walking them (Svelte's `html.js` claims siblings up to its empty-comment anchor and writes nothing); after a client navigation, or when its props change, it renders from its own chunk. No wrapper element is needed, so it works inside `<table>`, `<ul>`, and `<p>`, which is what blocked the general version
- the component's own scoped CSS travels with it (Svelte scopes styles per component, and a parent's styles don't reach it without `:global`), which is what blocked styled regions
- 1.1's island inference accepts static components inside an island's snippet, so many more islands become `hydrate="never"`
- the expected gain is bytes and per-component hydration: measured 1.6 ms against 0.8 ms for 200 instances on desktop, and the components' code leaves the initial load. The docs don't promise savings for plain markup
- kill criterion: if the adopted DOM after a scripted prop change ever differs from a fresh render, static components stay opt-in (`islands({ staticComponents: true })`) instead of on by default

### 6. One code path

- the plugin is required. Without it, the server has a second path (the small-inline-part shortcut in `island.svelte`) and nothing splits, and sections 1 to 5 need it. `svelte-islands migrate` adds it
- the post-build patching of output files and the splicing into Vite's plugin array (`vite.ts`) are replaced by `generateBundle` and documented plugin ordering, with unit tests on a scratch Vite build
- the route-to-csr map from 1.1 becomes the only shell detection; the `NATIVE` regex is removed

### 7. A smaller, clearer API

- `islands()` is the Vite plugin, and only that. The server handle and the transport become internal under zero-config, or `islandsHandle` and `islandsTransport` with `hooks: false`
- the seven low-level exports (`learn`, `load`, `loadNow`, `peek`, `replay`, `whenWanted`, `unroll`) move to `svelte-islands/advanced`
- `render` gains `"streamed"`; `render`, `reveal`, and `hydrate` keep their meanings (where the HTML comes from, when deferred HTML arrives, and when the code wakes), and the docs get one timeline diagram for all three
- `reader` joins `render="fresh"`
- the skeleton code is consolidated from four stores (server exemplars, `skeletons.json`, `localStorage`, and the in-memory map) into one model with one read and one write path, and the regex tokenizer (`skeleton.ts`) is replaced with a small streaming HTML tokenizer on the server
- `svelte-islands migrate` rewrites imports, adds the plugin, removes the hooks lines that zero-config replaces (or adds `hooks: false` when they're customized), and moves advanced imports

### 8. A native boundary, when Svelte has one

If Svelte ships a deferred-hydration boundary (the RFC draft in `plans/drafts/` proposes `<svelte:boundary hydrate={trigger}>`), the island runtime uses it when available: no `{@html}` adoption, no separate `hydrate()` roots, no copied contexts, and no rewriting of page-state references. The userland path stays for older Svelte versions. Nothing else in 2.0 depends on it.

## Upstream asks, with numbers

These need SvelteKit changes. The library prepares the case and the code; the owner opens each issue or PR.

- page-data trimming: the transport encoder sees only a value, not its key path (devalue's replacer is `(value, uneval)`), and decoding is synchronous, so a library can't leave a key out of page data safely. The ask: call `transport` encoders with `{ key, route }`, or a page option such as `serialize = { omit: [...] }` with a per-key fetch. Until then, `part()` and the page-data advisor do this by hand
- deferring Kit's client: on the docs site, the Kit and route-node chunks a page preloads are about 27.9 KiB gzipped out of 67.9 KiB, which a page could skip until navigation intent. Doing it in a library takes two pattern-matched rewrites of Kit's output (the start script, and the streamed-promise prelude that imports `start` and `app` eagerly whenever `transport` has entries), which fails this plan's rule against fragile coupling. The ask: a supported boot hook, such as a `start` option in `hooks.client` or a page option to start the client on intent
- kit#17763: the PR drafted in 1.1's owner actions
- kit#11724 (render-mode disclosure): offer the route-to-csr map the plugin already builds as prior art

## Adoption

What makes a library the default is mostly not code:

- the `@svelte-islands` npm organization, for the `sv` add-on
- a listing on svelte.dev's packages page
- a starter (`npx sv create` with the add-on, plus the docs' tutorial app as a template repo)
- the electionsarchive.com case study, with before and after numbers
- the benchmark entries from 1.1, posted, and their results linked from the README whatever they show
- co-maintainers before 2.0 work starts: the issue in `plans/drafts/` goes out first, because sections 2 to 5 are each a maintainer's worth of work
- a talk proposal for the next Svelte Summit, built on the benchmark and the RFC

## What 2.0 won't do

- resumability: core declined it, and it needs a different component model
- a client router: Kit's router, Speculation Rules, and cross-document View Transitions cover it
- a fork or patched build of Svelte or Kit
- static regions in arbitrary markup: measured no faster for plain markup, and blocked by CSS scoping and table contexts
- page-data trimming and deferred Kit boot without Kit's help: both would depend on matching Kit's generated output
- compile-time wrapping of `load` returns in `part()`: it changes the data contract and makes caching implicit; the advisor suggests it instead

## Watch list

- Compression Dictionary Transport (RFC 9842): Chromium only. Revisit delta parts, with each part's previous version as its dictionary, when another engine ships it
- streaming HTML insertion (`streamHTMLUnsafe`, Chromium and Edge 157): could replace section 2's swap script
- `prerender_until_script`: an origin trial; a fit for shell pages once it's stable
- `moveBefore()` (Chromium and Firefox): lets the swap script and fresh islands move nodes without losing focus, with `insertBefore` as the fallback
- service worker static routing (`addRoutes`, Chromium and Safari 27): route `/_parts/*` past the worker in `svelte-islands/sw`
- remote functions leaving `experimental` in Kit: readers as remote queries

## Risks

- sections 1, 3, and 5 couple the library to Kit's generated modules and Svelte's hydration markers. Every coupling asserts its shape and fails the build loudly, and the weekly CI leg runs against Svelte and Kit `@latest` so a change shows up within a week
- streaming changes the response shape. Each adapter gets an e2e test that checks the skeleton arrives before the island's content
- running page scripts on shell pages runs code that didn't run before. The rules are conservative, the opt-out is one export, and the fallback is 1.1's behavior
- signed scopes need a key that's the same everywhere. `init` generates it, the docs cover rotation (accept the previous key for one deploy), and the server refuses to start a reader path without it in production
- one maintainer can't own all of this. The sequence below is ordered so each step ships on its own

## Sequence

1. zero-config setup and the `sv` add-on (section 1), with the plugin required (section 6); this is also what `migrate` needs
2. shell pages that run their script (section 3)
3. static components (section 5)
4. readers for fresh islands (section 4)
5. streamed islands (section 2), behind `experimental.async`
6. the API cleanup and skeleton consolidation (section 7), then `migrate`
7. release 2.0, rerun every benchmark, and publish the results
